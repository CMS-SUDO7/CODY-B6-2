# 설계와 옵션 비교

README에서 분리한 옵션 설명, 설계 이유, PR 검토 기준입니다. 기본 실행 방법은 [README](../README.md)를 참고합니다.

## 옵션 선택과 비교

`--model`로 모델을 바꾸면 접근 권한이나 버전이 달라져도 소스를 수정할 필요가 없습니다.
`--temperature`는 표현의 다양성을, `--max-tokens`는 출력 상한을 조절합니다.
비교할 때는 같은 diff와 프롬프트를 사용하고 모델 이름, 옵션, 실행 시각을 기록합니다.
서버 모델 갱신과 샘플링 때문에 같은 설정에서도 문구가 달라질 수 있습니다.

```powershell
# 같은 미커밋 변경에서 temperature만 비교
python main.py pr --temperature 0.2 --max-tokens 2048
python main.py pr --temperature 1.2 --max-tokens 2048

# temperature를 유지하고 출력 상한만 비교
python main.py pr --temperature 0.2 --max-tokens 64
python main.py pr --temperature 0.2 --max-tokens 4096
```

### temperature

temperature는 다음 토큰을 선택할 확률 분포를 조절합니다. 일반적인 샘플링 모델에서는 `p(i) ∝ exp(logit(i)/T)`로 나타냅니다.
T가 낮으면 확률이 높은 후보에 집중하고, 높으면 후보 간 확률 차이가 줄어듭니다. T=0은 이 식에 직접 대입하지 않고 별도로 처리합니다.
모델마다 구현과 권장값이 다를 수 있습니다. [공식 생성 설정](https://ai.google.dev/api/generate-content#v1beta.GenerationConfig)

같은 `print(1) → print(2)` 변경도 `fix: 출력 값 변경` 또는 `fix: 샘플 출력의 기대값을 2로 조정`처럼 표현할 수 있습니다.
이 문구는 설명용 예시입니다. temperature를 높인다고 요약이 더 정확해지거나 제목과 본문의 연결이 좋아지지는 않습니다.
제목·Why·What·검증이 같은 변경을 설명하는지는 diff, reason, test와 대조해야 합니다.
낮은 값도 동일한 결과를 보장하지 않으며, 한 번의 결과 차이로 설정의 효과를 단정할 수 없습니다.

### max_tokens

`--max-tokens`는 목표 길이가 아니라 출력 상한이며, REST 요청의 `maxOutputTokens`로 전달됩니다.
입력 프롬프트도 토큰을 사용합니다. 이 도구는 문자·줄 수만 제한하므로 실제 토큰 수와 모델 한도를 검사하지 않습니다.
입력 토큰 수는 모델의 `countTokens`, 실제 사용량은 응답의 `usageMetadata`로 확인할 수 있습니다. [공식 토큰 안내](https://ai.google.dev/gemini-api/docs/tokens)

학습용으로 입력과 출력이 총 컨텍스트 8,192토큰을 공유하고 출력 한도가 2,048토큰인 모델을 가정해 봅니다.
입력이 7,000토큰이면 출력에 쓸 수 있는 공간은 `min(2,048, 8,192 - 7,000) = 1,192`토큰입니다.
이는 가상 모델의 계산 예시입니다. Gemini에서는 사용하는 모델의 입력·출력 한도를 각각 확인해야 합니다.

출력 예산이 부족하면 PR JSON이 `{"title":"...","why":[`처럼 중간에 끊길 수 있습니다.
실제 응답이 `MAX_TOKENS`이면 오류로 종료하고 미완성 초안을 출력하지 않습니다.
입력 한도를 넘은 경우에는 diff를 줄여야 합니다. 사고 기능을 사용하는 모델은 사고 토큰도 출력 예산을 소비할 수 있습니다. [공식 사고 토큰 안내](https://ai.google.dev/gemini-api/docs/thinking)

### 실제 비교 결과

2026-10-08 15:59 KST에 `gemini-3.1-flash-lite`로 실행했습니다.
입력은 `app.py`의 `print(1) → print(2)`로 고정했고, 각 조건을 1회씩 실행했습니다.

| temperature | max_tokens | 결과 | 원문 로그 |
| --- | --- | --- | --- |
| 0.2 | 2048 | 종료 0, 제목 `app.py 출력값 변경`, PR 3개 섹션 완성 | [기준 PR](evidence/live/pr-baseline.txt) |
| 1.2 | 2048 | 종료 0, 제목 `app.py 샘플 출력 기대값 변경`, PR 3개 섹션 완성 | [temperature 변경](evidence/live/pr-temperature.txt) |
| 0.2 | 64 | 종료 1, `MAX_TOKENS`, 미완성 초안 출력 없음 | [작은 예산](evidence/live/pr-small-budget.txt) |
| 0.2 | 4096 | 종료 0, 기준 PR과 같은 제목·본문 | [큰 예산](evidence/live/pr-large-budget.txt) |

제목과 요약의 표현 차이는 관측했지만 각 조건을 한 번만 실행했으므로 temperature의 일반적인 효과를 입증한 결과는 아닙니다.
이 입력에서는 64토큰이 부족했고 2048과 4096은 충분했습니다. 두 성공 결과가 같았듯이 상한을 늘려도 글이 길어지는 것은 아닙니다.

`python scripts/capture_evidence.py --live`로 같은 조건을 기록할 수 있습니다.
명령, 종료 코드, stdout/stderr와 작은 예산의 실패를 함께 저장합니다. 자세한 실행 방법은 [평가 항목과 실행 증거](evaluation.md)에 있습니다.

## 프롬프트와 후처리

`build_prompt`는 diff, status, reason, test를 바탕으로 내용과 JSON 필드를 요청합니다.
`format_draft`는 반환된 JSON의 제목 길이와 PR 섹션 구조를 정리합니다.
프롬프트는 내용 생성에, 후처리는 복사할 텍스트의 형식에 집중하도록 나눴습니다.
형식 규칙은 네트워크 없이 검사할 수 있지만 두 단계의 필드 이름은 함께 관리해야 합니다.

| 방식 | 할 수 있는 일 | 한계와 비용 |
| --- | --- | --- |
| 후처리 — 현재 사용 | 제목 길이와 헤더를 일정하게 맞추고 누락 항목에 안내문 보충 | 추가 API 호출 없음. 사실 오류를 고치지 못하며 잘린 제목은 의미 확인 필요 |
| 자동 재생성 | 규칙과 누락 내용을 모델에 다시 요청 | 정확성·형식 준수 보장 없음. 응답이 달라질 수 있고 추가 대기·할당량·반복 제한 관리 필요 |

현재 구현은 생성 요청을 1회로 제한하고 후처리로 형식을 정리합니다.
빈 제목, 잘못된 JSON, 미완료 응답은 오류로 처리합니다. 다시 생성하려면 입력이나 설정을 고친 뒤 재실행합니다.
후처리는 변경 배경이나 테스트 결과의 사실 여부를 판단하지 못합니다.

커밋 제목은 한 줄로 정리해 최대 72자로 제한하고, 50자를 넘으면 권장 길이 경고를 출력합니다. 본문은 불릿 2개까지 사용합니다.
PR 제목은 최대 80자이며 `Why`, `What`, `How to Test` 헤더를 코드에서 붙입니다.
빈 섹션에는 미확인·미실행 안내를 보충합니다.

## PR 초안 검토

아래는 작성 예시입니다. 실제 변경과 관측 결과로 바꾸고, 실행하지 않은 검증은 미실행으로 표시합니다.

```markdown
fix: 빈 입력 실행 오류 처리

## Why
- 빈 입력에서 예외가 발생해 실행을 완료하지 못함

## What
- main.py에서 빈 입력을 검사하고 안내 후 종료하도록 변경

## How to Test
- 실행 명령: [명령]
- 기대 결과: [기대값]
- 확인 결과: [실제로 관측한 결과]
- 미실행 항목: [대상과 검증 제안]
```

- 제목과 What이 실제 파일과 전후 동작을 설명하는지 확인합니다.
- Why에 확인하지 않은 이유를 사실처럼 적지 않았는지 확인합니다.
- 테스트 명령, 관측 결과, 미실행 검증 제안을 구분합니다.
- 특정 사람이나 팀을 근거 없이 탓하는 표현이 있는지 확인합니다.
- 생략된 입력, 미추적·바이너리 파일의 확인 범위, 민감정보, 잘린 제목의 의미를 검토합니다.

reason이나 test를 제공하지 않았다면 배경 미확인·테스트 미실행 표시를 유지합니다.
모듈별 수정과 검증 방법은 [유지보수 지침](maintenance.md)에 정리했습니다.
