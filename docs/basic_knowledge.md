# 이 미션에서 배우는 것

이번 미션의 목표는 **바뀐 코드 → Git diff → Python의 API 요청 → AI의 초안 → 사람이 검토하는 커밋·PR**의 흐름을 연결하는 것입니다. AI 모델 자체를 학습시키는 과제가 아니라 이미 제공되는 모델을 프로그램에서 사용하는 과제입니다.

## 1. 먼저 필요한 Python 기초

### 값과 자료구조

문자열은 제목과 diff 같은 글을 저장합니다. 리스트는 `['git', 'diff']`처럼 순서가 있는 항목을 저장합니다. 딕셔너리는 `{'model': 'gpt-5-mini'}`처럼 이름으로 값을 찾습니다. 함수가 `return status, diff`로 두 값을 반환하면 튜플로 묶이고 `status, diff = ...`로 각각 받습니다.

`len(text)`는 Python 문자열의 문자 수입니다. UTF-8 바이트 수나 AI 토큰 수와 같지 않습니다. 파일에서 한 줄로 보여도 한글을 UTF-8로 바꾸면 여러 바이트가 될 수 있습니다.

### 함수·조건·반복

`def`는 동작을 이름으로 묶습니다. `collect_changes()`는 Git 조회, `request_text()`는 통신, `render_draft()`는 출력 정리 담당입니다. 함수의 `return`은 값을 호출자에게 돌려주고 `print()`는 화면에 보여 줍니다.

`if not key:`는 키가 비어 있는지 판단합니다. `for line in text.splitlines():`는 문서를 한 줄씩 읽습니다. `continue`는 이번 반복의 나머지를 건너뛰고, `break`는 반복 전체를 끝냅니다.

### 예외와 자원 관리

`try/except`는 실패를 정상 흐름과 구분합니다. `raise RuntimeError(...)`로 오류를 전달하면 main이 안내를 출력합니다. `finally`는 함수 중간에 return해도 실행되므로 호출 횟수를 남기기에 적합합니다.

`HTTPError`를 처리하던 중 그 오류 본문을 읽는 작업도 실패할 수 있습니다. 이번에 나온 IncompleteRead가 그 예입니다. 그래서 오류 응답을 읽는 부분에도 별도의 try/except가 필요합니다. `with opener.open(...) as response:`는 응답 자원을 사용한 뒤 닫아 줍니다.

### 모듈과 실행 위치

`.py` 파일 하나가 모듈입니다. `from formatting import parse_draft`로 다른 모듈의 함수를 가져옵니다. `if __name__ == '__main__':`는 직접 실행할 때만 main을 시작하므로 import만 했을 때 API가 호출되지 않습니다.

현재 작업 폴더와 main.py가 저장된 폴더는 다를 수 있습니다. 이 도구는 현재 폴더의 Git을 읽습니다. 다른 미션 저장소의 루트에서 도구 파일의 절대 경로를 실행할 수도 있습니다.

### 별표, get, None

`run_git(*arguments)`의 정의에서 별표는 여러 인수를 모읍니다. `run_git(*options, '--', *paths)`의 호출에서는 리스트 항목을 인수로 펼칩니다.

`os.environ.get('AI_API_KEY', '')`는 이름이 있으면 값을, 없으면 빈 문자열을 돌려줍니다. `None`은 값이 지정되지 않았음을 나타냅니다. 이번 코드의 temperature 기본값은 None이어서 해당 필드를 요청에 넣지 않습니다. 0을 넣는 것과는 다릅니다.

## 3. 핵심 지식

### Git 변경 영역을 구분하기

파일이 A였는데 B로 고치고 git add한 뒤 C로 다시 고쳤다고 생각해 보세요. 스테이징 diff는 A→B, 미스테이징 diff는 B→C입니다. `--staged`를 쓰면 A→B만 읽습니다. 파일을 교체한 뒤 git add를 다시 하지 않으면 계속 이전 차이가 나오는 이유입니다.

diff의 `+`는 추가, `-`는 삭제이고 `@@`는 위치 정보입니다. `+++`와 `---`는 파일 헤더입니다. 줄 수에는 이런 설명 줄도 들어갑니다. 2900이라는 숫자는 미션 규칙이나 상수가 아닙니다.

`subprocess.run(['git', ...], capture_output=True, ...)`는 Git 실행 결과를 Python 문자열로 받습니다. 명령 인수를 리스트로 전달하므로 셸 명령 문자열을 조립하지 않습니다. 수집 범위는 status/diff이며 Python이 자동으로 커밋하거나 push하지 않습니다.

### REST 요청의 구성

`build_payload()`는 모델과 메시지를 딕셔너리로 만듭니다. `json.dumps()`는 그것을 JSON 문자열로, `.encode('utf-8')`는 전송할 바이트로 만듭니다. `urllib.request.Request`에 POST 주소, 인증 헤더, 본문을 넣고 opener가 전송합니다.

응답에서 읽는 바깥 JSON은 아래처럼 생겼습니다. 예시는 구조 설명용입니다.

```json
{
  "choices": [{
    "finish_reason": "stop",
    "message": {"content": "제목: fix: 안내 개선\n\n- 빈 입력 안내 추가"}
  }]
}
```

바깥 자료는 `json.loads()`로 해석합니다. 그러나 `message.content`는 **Markdown 문자열**이므로 일반 경로에서는 다시 JSON으로 해석하지 않습니다. 이전에는 AI가 그 안에도 정확한 JSON을 써야 했고, 쉼표 하나가 빠져도 전체 초안 처리가 실패했습니다. 이제 기본 문서 형식에서 그 의존을 없앴습니다. 과거처럼 정상 JSON을 보낸 경우만 호환 변환합니다.

### 프롬프트와 생성 옵션

system 메시지에는 역할, 한국어, 출력 양식, 제목 길이, 사실성 기준을 넣습니다. user 메시지에는 실제 diff와 `--reason`, `--convention`을 넣습니다. 커밋 명령은 커밋만, PR 명령은 PR만 요청해 불필요한 중첩 구조를 줄입니다.

diff는 무엇이 달라졌는지 보여 주지만 왜 바꿨는지는 충분히 설명하지 못합니다. `--reason`으로 사람이 알고 있는 목적을 제공하는 이유입니다. 입력에 포함된 문서의 기능 설명을 실제 구현 증거로 착각하지 않도록 지시도 추가했습니다.

temperature는 결과의 변동성에 영향을 줄 수 있지만 사실 오류를 없애지 않습니다. 출력 토큰 상한은 생성 가능한 출력량에 영향을 주며 너무 작으면 응답이 중단될 수 있습니다. 모델에 따라 이 상한에 추론 토큰이 포함될 수도 있으므로 문자 수 제한과 동일하게 생각하지 않습니다. 이번 기본 요청은 두 옵션을 생략해 서버 기본 동작을 사용합니다. 필요할 때 CLI로 지정하면 실제 요청 필드에 들어갑니다.

### 통신 실패와 문서 형식 실패를 분리하기

HTTP 401은 인증 단계, HTTP 400은 서버가 요청을 거절한 단계입니다. API 호출은 성공했지만 제목을 못 찾는 경우는 문서 해석 단계입니다. 같은 재시도 정책으로 묶으면 안 됩니다.

통신 실패에는 자동 재시도가 없습니다. 완성된 응답 텍스트의 형식만 읽을 수 없을 때 한 번 더 정리를 요청합니다. 최대 2회이며, 두 번째는 기존 원문을 정해진 양식으로 바꾸도록 요청합니다. 출력 자체가 잘렸다면 없는 내용을 복원할 수 없으므로 미완성이라고 표시합니다.

서버가 성공 응답을 보냈다는 것과 좋은 커밋 메시지가 만들어졌다는 것도 다릅니다. 제목·길이·섹션은 Python이 검사할 수 있지만, 실제 의도나 테스트 결과가 맞는지는 작성자가 확인해야 합니다.

### 마스킹과 전송량 제한

여러 줄 개인키를 가리려면 시작과 끝을 함께 볼 수 있어야 합니다. 그래서 마스킹을 먼저 한 뒤 diff를 자릅니다. 현재 구현은 앞에서부터 최대 파일 블록 수·줄 수를 선택하므로 큰 첫 파일이 대부분의 공간을 쓸 수 있습니다. `--files`는 이런 상황에서 대상 파일을 줄이는 옵션입니다.

문자 수 C인 diff에 `splitlines()`를 적용하면 O(C) 시간과 메모리가 필요합니다. 줄 선택 반복은 전체 N줄 중 제한에 걸릴 때까지 읽습니다. 안전 모드는 전송량을 제한하지만 Git 출력을 처음부터 작게 읽어 오는 기능은 아닙니다. 외부 Git 처리 시간과 AI 응답 시간은 이 반복문의 시간 계산과 별개입니다.

## 4. 작은 연습

1. **결과 예상:** 아래 코드를 실행하면 API가 호출될까요? 어떤 PR 섹션이 나올까요?

```python
from formatting import parse_draft, render_draft
draft = parse_draft('pr', '제목: fix: 안내 개선\n## What\n- 안내 문구 수정')
document, warnings = render_draft('pr', draft)
print(document)
print(warnings)
```

2. **값 추적:** `limit_diff()`에서 `max_files=1`이고 두 번째 `diff --git` 줄을 만났을 때 files와 selected를 추적하세요.
3. **수정 연습:** main.py에서 `--max-lines` 기본값을 200에서 100으로 바꾸고 README의 기본값도 수정하세요. 100줄이 넘는 변경에 `--safe-mode --dry-run`을 실행해 차이를 확인하세요. API 키는 필요 없습니다.

해설: 1번은 순수 문자열 처리이므로 호출이 없습니다. Why/What/How to Test가 모두 나오며 Why와 How to Test에는 확인 필요 불릿과 경고가 생깁니다. 2번에서 files는 2가 되지만 제한을 넘었으므로 두 번째 파일 헤더를 selected에 넣기 전에 break합니다. 3번은 기본값을 쓰는 실행만 바뀌며 `--max-lines 200`을 명시한 실행은 200을 사용합니다.

## 5. 이후 확장할 주제

- 자동 검증: 실제 서버 호출과 모의 통신 검사를 구분하고 오류 경로를 재현하는 방법.
