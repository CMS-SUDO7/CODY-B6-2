# B6-2 코드 흐름과 줄별 해설

2026-10-16 기준으로 현재 작업 트리의 6개 Python 소스와 대조했습니다. 아래 줄별 표는 현재 코드·줄 번호를 인용하며, 여러 줄 비밀값 처리, 공통 요청 본문, API 키 오류 판별, 출력 보정 안내까지 포함합니다. 입력·출력 상한과 Git 제한 시간을 상수로 묶고 JSON 인용부호 판별·YAML 블록 탐색을 분리한 코드에 맞춰 갱신했습니다. CLI 검증 범위와 오류 안내는 같은 상수를 사용하며, 마스킹 조건·diff 블록 수·API 요청 시도 수의 이름을 명확히 했습니다. 실행 방법과 실제 Gemini 실행 기록은 [README](../README.md), 기초 개념과 학습 과제는 [기초와 핵심 지식](basic_knowledge.md)을 참고하세요.

## 1. 파일 역할과 시작점

현재 학습에 필요한 파일 구조는 다음과 같습니다. Git 내부 자료와 실행 중 생기는 캐시는 생략했습니다.

```text
CODY-B6-2/
├── main.py
├── cli.py
├── git_changes.py
├── safety.py
├── gemini_api.py
├── output_format.py
├── README.md
├── .gitignore
└── docs/
    ├── code_translation.md
    ├── basic_knowledge.md
    ├── verification.md
    └── B6-2 내가 고친 코드 설명을 AI가 대신 써주는 도우미 만들기.pdf
```

Python 표준 라이브러리만 사용합니다. 별도 패키지 설치 파일이나 테스트 폴더는 없으며, 재현 가능한 검증 예제는 README에 있습니다. docs/verification.md는 초기 Linux 실행 기록입니다.

실행 시작점은 `main.py` 마지막의 `sys.exit(main())`입니다. `main()`은 `cli.py`의 `parse_args()`로 옵션을 읽고, `collect_changes()`로 저장소 자료를 모으고, `prepare_input()`으로 전송 자료를 다듬습니다. `build_prompt()`로 프롬프트를 만든 뒤 실제 생성에서는 `generate()`를 한 번 호출하고 `format_draft()` 결과를 화면에 보여 줍니다. `--dry-run`은 `build_payload()`로 같은 요청 본문을 만들어 출력하고 API를 호출하지 않습니다.

| 파일 | 책임 | 호출 관계 |
| --- | --- | --- |
| main.py | 실행과 사용자 안내 | 아래 다섯 모듈의 함수를 호출 |
| cli.py | 명령줄 옵션 해석과 검증 | parse_args → argparse |
| git_changes.py | Git 읽기 | collect_changes → run_git → 외부 Git |
| safety.py | 입력 제한과 마스킹 | prepare_input → mask_sensitive → 내부 비밀값 탐색 |
| gemini_api.py | 프롬프트와 REST | build_prompt; generate → build_payload/urlopen, 키 오류 판별·마스킹 |
| output_format.py | 텍스트 형식 보정 | format_draft → one_line/get_items |

commit/pr 모두 현재 미커밋 변경의 staged와 unstaged를 수집합니다. README만 스테이징했어도 미스테이징 Python 변경이 초안에 포함될 수 있습니다. staged만 선택하는 옵션이나 브랜치 간 커밋 비교는 구현하지 않았습니다. 실제 커밋에 적용할 메시지는 인덱스 범위와 대조해야 합니다.

Git 쓰기 명령은 실행하지 않습니다. 데이터 수집에만 status/diff를 사용하고 루트 확인에 rev-parse를 보조로 사용합니다. 외부 AI에게서 온 문자열을 코드로 실행하지 않습니다.

## 2. 주요 함수의 입력·반환·오류

| 함수 | 입력 | 반환과 데이터 변화 | 필요한 오류 처리 |
| --- | --- | --- | --- |

| run_git | Git 인자 문자열 리스트 | stdout 문자열, Git 읽기만 수행 | 설치 누락·30초 초과·명령 실패 |
| collect_changes | 현재 실행 폴더 | status/diff/count/untracked 튜플 | 저장소 아님·루트 아님·병합 충돌 |

| prepare_input | status/diff/reason/test, 안전 모드, 키 | 전송 dict와 생략 bool; 지역 dict 값 정리 | 일부 생략을 omitted로 전달 |
| build_prompt | command, 전송 dict | 프롬프트 문자열 | 호출자는 commit/pr만 전달 |
| build_payload | 프롬프트, temperature, max_tokens | contents/generationConfig dict, 키 제외 | dry-run과 실제 요청이 공유 |
| _is_invalid_api_key | 서버 오류 본문 문자열 | 명시적인 키 오류 여부 bool | 비JSON·다른 구조면 False, reason 우선 |
| generate | 프롬프트, 키, 모델, 생성 옵션 | AI 초안 dict, 외부 생성 요청 1회 | HTTP·연결·timeout·JSON·미완료 |
| one_line | 임의 객체 | 정리된 문자열, 비문자열은 빈 문자열 | 호출자가 누락으로 처리 |
| get_items | 초안 dict, 키, 대체 안내 | 유효 불릿 list 또는 안내 1개 | 잘못된 타입/빈 항목을 제거 |

반환은 호출자에게 값을 전달하는 작업이고 print는 화면에 보여 주는 작업입니다. 이 구현은 main에 출력 책임을 모으고 다른 함수는 대부분 값을 반환합니다. 실제 파일 저장, Git 커밋, PR 게시를 하지 않습니다.

CLI 검증과 오류 안내, 입력 길이 검사와 자르기는 각각 같은 상수를 사용합니다. 프롬프트의 제목·불릿 기준도 출력 모듈의 상수를 공유합니다. 기존 제한값과 동작은 유지했습니다.

## 3. 작은 입력을 끝까지 따라가기

임시 저장소의 app.py가 처음에 `print(1)`이었다가 `print(2)`로 변경됐고 아직 git add하지 않았다고 합시다. `GEMINI_API_KEY`가 설정된 상태에서 `python main.py commit --reason "예제 출력 변경"`을 실행합니다.

1. `parse_args()`의 command는 commit, temperature는 1.0, max_tokens는 2048, safe_mode는 True입니다.
2. `collect_changes()`는 status의 `" M app.py"`를 담고 count=1, untracked=0을 반환합니다. staged는 빈 문자열이고 unstaged에는 `-print(1)`과 `+print(2)`가 있습니다.
3. `prepare_input()`은 자료에서 민감값을 가리고 이번처럼 작은 diff는 자르지 않아 omitted=False입니다. test는 빈 문자열입니다.
4. `build_prompt()`는 summary/title/changes 형태를 요청하며 테스트 성공을 지어내지 말라는 규칙을 붙입니다.
5. `api_request_attempts=1`이 된 뒤 `generate()`가 POST를 한 번 시도합니다. 다음 초안은 흐름 설명을 위한 **모의 결과**입니다.

```json
{"summary":"app.py 출력 값을 변경했습니다.","title":"fix: 예제 출력 값 수정","changes":["app.py 출력 값을 1에서 2로 변경"]}
```

6. `format_draft()`에서 제목은 제한 안이므로 notices=[]입니다. 본문은 `- app.py 출력 값을 1에서 2로 변경`이고 반환은 제목+빈 줄+본문, 빈 경고 목록입니다.
7. `main()`이 변경 요약과 커밋 메시지 구역을 출력하고 0을 반환합니다. finally에서 호출 1회를 출력하고 sys.exit가 0을 운영체제에 전달합니다.

API 키가 없다면 5번 전 키 확인에서 오류가 나고 요청은 0회입니다. --dry-run이면 4번의 프롬프트와 build_payload가 만든 요청 JSON을 출력하고 0회로 끝납니다. HTTP 429면 요청 시도는 1회지만 초안은 출력하지 않고 오류와 제한 안내를 출력합니다.

## 4. 줄별 해설 읽는 방법

현재 소스의 원본 줄 번호와 코드 문자열을 아래 표에 대조했습니다. 이 문서에서는 빈 줄, import, 주석, 독스트링, 닫는 괄호·구분 기호만 있는 줄을 제외합니다. 반복되는 실행 줄과 여러 줄 문장의 각 줄은 생략하지 않습니다. 모듈 수준의 상수와 비밀값 패턴 정의도 포함합니다. 여러 줄 import는 구성요소까지 제외합니다. 코드를 수정하면 해당 줄 번호·인용 코드·설명을 함께 갱신해야 합니다.

표의 코드 칸은 공백을 보존하도록 표시합니다. 여러 줄 문장은 각 줄을 별도로 설명합니다.

## safety.py

마스킹은 현재 키 → URL 인증 정보 → Authorization/Bearer/Basic → PEM 개인키 → 이름이 있는 비밀값 → 알려진 키·이메일 순으로 처리합니다. `_quoted_end()`는 인용 값의 끝, `_compound_end()`는 중첩 괄호의 끝을 찾고, `_is_escaped_quote_end()`는 JSON 인용부호 판별을 맡고 `_yaml_block_end()`는 들여쓰기로 YAML 블록 끝을 찾습니다. `_mask_assignments()`는 보조 함수가 찾은 위치를 이용해 여러 줄 값 전체를 가립니다. 이후 `prepare_input()`이 크기를 제한합니다.

## gemini_api.py

`build_payload()`는 dry-run과 실제 POST가 공유하는 요청 본문을 만듭니다. `_is_invalid_api_key()`는 HTTP 상태만으로 키 오류를 단정하지 않고 서버 본문의 reason을 우선 확인합니다. 생성 응답은 바깥 JSON과 그 안의 초안 JSON을 각각 해석합니다.

제목 길이와 커밋 불릿 상한은 output_format.py에서 가져와 프롬프트와 후처리가 같은 상수를 사용합니다.

상세 오류는 일반 반복문에서 타입·reason 값을 단계별로 검사합니다. 유효한 reason이 있으면 메시지 접두사보다 우선하는 기존 규칙을 유지합니다.
